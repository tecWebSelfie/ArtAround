## Findings

### F1 — Another user's private content is readable through one's own private tour + the group cookie

- Severity: **High**. Confidence: confirmed (reproduced from fresh users).
- Preconditions: user V has a private content C. Its id is discoverable from
  `GET /api/objects/:id?depth=0` → `contents`. Attacker X is signed in.
- Steps:
  1. X sends `POST /api/tours {visibility:'private', museum, contents:[X's public c1, C]}` → 201.
  2. X sends `POST /api/rooms {tourId}`, then `POST /api/rooms/token` (host key) → `aa-group-tour` cookie.
  3. `GET /api/contents/C` with that cookie, from any client including anonymous.
- Variant: take the cookie on a tour with public stops only, then PATCH the
  tour to add C.
- Expected: 404. Actual: 200 with C's title and body. Without the cookie: 404.
- Cause: `guardTourContents` (`src/collections/Tours.ts:~103`) only refuses
  private stops in _public_ tours. `groupTourContentIds`
  (`src/lib/visibility.ts:~110`) then unlocked every id the tour lists, read live.
- Spec: `tests/int/nightly/private-content-via-group-cookie.int.spec.ts` (e9bb5c5). It failed on TESTED_SHA and passes after the fix.
- Fix status: **fixed in c1e2b10**. The cookie now unlocks only the tour's
  contents that are public or authored by the tour's author. Docs are updated
  in `docs/permissions-and-editing.md`, and the mock in
  `tests/int/visibility.int.spec.ts` now gives the fake tour an author.
- What to check in review: product trade-off. A group guest's visit copy of
  a host's private tour keeps the host's private stops, but the copy's own
  group cannot read them (they are not its author's). Saving such a tour is
  still allowed. Decide whether `guardTourContents` should also refuse
  another author's private stops outside visit copies.

### F2 — Anonymous email oracle on `users`

- Severity: **Medium**. Confidence: confirmed.
- Steps: `GET /api/users?depth=0&where[email][equals]=<address>` with no
  auth → `totalDocs: 1` (0 for unknown addresses). `where[email][like]=<prefix>`
  also matches, so full addresses can be extracted character by character.
  `sessions.id` is also filterable.
- Expected: no match, or 400/403. Actual: the filter acts as an oracle. The
  returned document hides the email, but the match itself leaks it.
- Cause: `src/collections/Users.ts:83`. `hidePrivateFields` is only an
  `afterRead` hook. `read: anyone` leaves `where` on `email` open, because the
  auth-injected field has no field-level read access (a deliberate choice,
  per the comment there).
- Spec: `tests/int/nightly/email-enumeration.int.spec.ts` (0faa9bb). It fails on TESTED_SHA and on the QA branch.
- Fix status: **needs maintainer**. The fix changes the auth collection's
  `email` field: either redeclare it with field read access, or refuse
  `email`/`sessions` in `where` for non-self callers in a `beforeOperation`
  hook. That is an auth design decision.

### F5 — `pnpm test:e2e` crashes before running any test

- Severity: **High** for delivery, because it very likely breaks the e2e
  step in CI. Confidence: confirmed locally on a clean checkout, Node 22.23.
  It is not confirmed on CI: there is no run history to check.
- Actual: `Cannot find module '.../node_modules/next/server' imported from src/lib/localized.ts`, then "No tests found".
- Cause: `package.json` has `"type": "module"`, so Playwright loads specs as
  ESM. `tests/helpers/seedUser.ts` imports `payload.config`, which leads to
  `src/lib/localized.ts:2` `import { after } from 'next/server'`. `next` has
  no `exports` map, so Node's ESM resolver needs `next/server.js`. The import
  arrived in 328efac.
- Fix status: **proposed fix in db9d0df, for maintainer review**. It was
  prepared after the maintainer allowed more work while away.
  `localized.ts` now imports `next/server.js`. Nothing else the helpers reach
  imports from `next/*`. Plain `pnpm test:e2e --list` lists 21 tests, and
  build, typecheck and lint pass.
