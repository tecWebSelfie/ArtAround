## Findings

### N1 — The quiz of a private tour is public

- Severity: **High**. Confidence: confirmed.
- Preconditions: user A has a private tour with a quiz. The tour id is known,
  for example from a shared link.
- Steps:
  1. Anonymously, or as user B, open `GET /en/tour/<id>/quiz` and `?q=1`.
  2. Call the `checkQuizAnswer` Server Function (`Next-Action`) with that
     tourId.
  3. Call `submitQuizAttempt`, then open `/en/tour/<id>/quiz/result/<token>`.
  4. Call `groupQuizScores` with that token.
- Expected: 404 or `invalid`, as for an unknown tour. `/en/tour/<id>` itself
  already answers 404.
- Actual:
  - The quiz page answers 200 and shows the private title, the prompts and the
    options.
  - `checkQuizAnswer` returns `status: ok`, `correctKey` and the explanation.
  - `submitQuizAttempt` stores an attempt.
  - The result page shows the title, the correct answers and the explanations.
- Cause: `getTourQuizForResult` (`src/lib/quiz.server.ts:~106`) read the tour
  with the Local API default, `overrideAccess: true`. The quiz page, the
  actions and the result page all depend on it.
- Spec: `tests/int/nightly/private-tour-quiz-leak.int.spec.ts` (61634af0),
  tests 1–3. They fail on TESTED_SHA and pass on the branch.
- Fix status: **fixed in 60d2c52e**. The tour is now read with `asViewer()`,
  which honours the visitor's own session and the group cookie, so group guests
  of a private class visit still take the quiz. `group-tour.e2e` passes 5/5.
- What to check:
  - A result link becomes 404 once the tour turns private, or once a group
    guest's 4 h cookie expires. This contradicts the comment "a score already
    earned must not be hidden". Decide which one wins.
  - A paid tour that the visitor hasn't bought keeps a public quiz. This is by
    design, and no locked body leaks, but it is a product question.

### N2 — A group-cookie holder can open their own room for someone else's private tour

- Severity: **Medium**. Confidence: confirmed.
- Steps:
  1. A opens a room on A's private tour.
  2. An anonymous guest joins and receives the `aa-group-tour` cookie.
  3. With that cookie only, the guest sends `POST /api/rooms {tourId}`.
     It answers 200 with a hostKey.
  4. The guest joins that room as `host`, which mints a fresh cookie.
- Expected: 404. Without the cookie, the same request answers 404.
- Actual: the guest becomes host of a new room. They can re-mint the 4 h
  cookie indefinitely, even after A ends the group, and invite anyone to read
  A's private tour and its private stops.
- Cause: `src/app/api/rooms/route.ts:~36` read the tour with `asViewer()`, and
  `tours.read` honours the group cookie (`src/lib/visibility.ts`).
- Spec: `tests/int/nightly/group-cookie-renews-itself.int.spec.ts` (dd4ee754).
- Fix status: **fixed in aedc3196**. A new Local API context flag,
  `IGNORE_GROUP_COOKIE`, is checked by `groupTourOf`, and `POST /api/rooms`
  sets it. Guests' reads are unchanged.
- What to check: the flag is opt-in, so any future endpoint that lets someone
  lead a group must set it as well.

### N3 — Guest identity takeover in a group room

- Severity: **Medium**. Confidence: confirmed, including with real LiveKit
  connections from headless Chrome.
- Steps:
  1. Guest V joins and gets identity `guest-<X-Guest-Id>`. Every participant
     can see it.
  2. Guest X sends `POST /api/rooms/token` with `X-Guest-Id: <V's id>`. It
     answers 200 with a token for V's identity.
  3. X connects with that token.
- Expected: one device cannot claim another device's identity.
- Actual:
  - V is disconnected at once (DUPLICATE_IDENTITY).
  - X then holds V's identity and can set V's `quizToken`, `quizDone` and
    `quizAnswered` attributes. The host board shows them as V's.
  - Any guest can keep kicking any other guest. The host identity is not
    reachable.
- Cause: `src/app/api/rooms/token/route.ts:42` uses the device's secret id as
  the public identity.
- Spec: `tests/int/nightly/group-guest-identity-takeover.int.spec.ts`
  (dd4ee754). It fails on TESTED_SHA and on the branch.
- Fix status: **needs maintainer**. The fix is ready, but it breaks an existing
  test's expectation, and this run never edits existing tests. Proposed patch:
  - `src/app/api/rooms/token/route.ts`: replace the identity
    `guest-${guestId.data}` with
    `'guest-' + createHmac('sha256', process.env.LIVEKIT_API_SECRET!).update(guestId.data).digest('hex').slice(0, 32)`
    (import `createHmac` from `node:crypto`). Client code never derives
    identities from `aa-guest-id`, so nothing else changes.
  - `tests/int/rooms-api.int.spec.ts:58`: replace
    `.toBe('token-for:guest-device-123456:Anna')` with
    `.toMatch(/^token-for:guest-[0-9a-f]{32}:Anna$/)`.
  - `docs/group-tours.md`: add one sentence saying the public identity is a
    keyed hash of the device id.

### N4 — The quiz-ownership error names another user's private tour

- Severity: **Low**. Confidence: confirmed.
- Steps: as user B, send `PATCH /api/tours/<B's tour>` with A's tour-owned
  question id in `quiz.questions`.
- Expected: a 400 that doesn't name the tour.
- Actual: 400 with "…belong to the quiz of «<A's private title>»". Before the
  N1 fix, the question ids could be read from A's quiz page.
- Cause: `src/lib/quiz-ownership.ts` (`validateQuizQuestions`) read the
  owning tour without access and quoted its title.
- Spec: `private-tour-quiz-leak` test 4.
- Fix status: **fixed in 0a282cae**. The title is quoted only when the caller
  can read that tour; otherwise the message says "another tour". The refusal
  itself is unchanged.

## Design questions (no spec)

- The group cookie outlives the group. After the host's `DELETE /api/rooms/CODE`,
  the guest's cookie still reads the private tour and its contents until it
  expires (4 h). This matches the docs, but ending a group doesn't revoke
  access.
- `x-forwarded-for` is trusted as sent, so a spoofed value per request bypasses
  the 10/min and 30/min limits on the room routes. This is the hypothesis of the
  last run, confirmed locally. Whether it matters depends on the production
  proxy.
- A `choices` body over 1 MB answers 500 (Next's Server Action body limit). It
  is not slow, and nothing is stored.

## Verified secure (area C)

- Room name race: 10 parallel creates with the same name give exactly one 200
  and nine 409. The winner's key stays host, and the name can be reused after
  DELETE.
- Host key: a wrong, empty or other room's key never yields `host`, and DELETE
  with it answers 403.
- Room and token inputs (codes, names, guest ids, tourIds, bodies) answer 4xx,
  never 500.
- Guest grants: no publishing and no data; only own metadata. Followers trust
  only the `host` identity (code reading).
- `groupQuizScores` rejects another tour's tokens, more than 200 tokens, and
  duplicates.
- Quiz grading clamps `stepsCompleted` and ignores foreign question ids.
- `quizQuestions` are not readable or writable across users, over REST or
  GraphQL.
