## Findings

### N6 — The body of a paid content is readable by anyone

- **Severity: Critical.** Confidence: confirmed. This is a complete paywall
  bypass that needs no account.
- **Preconditions:** a content with `price > 0`, and its id, which is public.
- **Steps:** as anonymous, or as a user who has not bought it:
  - `GET /api/contents/<id>?select[body]=true`;
  - or `GET /api/contents?where[id][equals]=<id>&select[body]=true`;
  - or `GET /api/tours/<tour>?depth=1&populate[contents][body]=true`;
  - or `GET /api/objects/<obj>?depth=3&populate[contents][body]=true`;
  - or `GET /api/content-audio/<id>`.
- **Expected:** no `body`, as with a plain `GET`, and `403 locked` for the audio.
- **Actual:**
  - 200 with the full Lexical body, marker text included.
  - `/api/content-audio` answers `ready` and streams the MP3 (200 audio/mpeg).
  - By reading the code: `/api/expand` with `target: objects` populates
    `{title, body}` without `price`. Locked bodies then enter the model prompt,
    and the generated text is saved into a public variant.
- **Cause:** `canReadPaidBody` (`src/collections/Contents.ts:63`) began with
  `if (!doc?.price) return true`. With a `select` or `populate`, `doc` is
  partial and has no `price`, so the content counted as free. The audio route
  reads with `select: { body: true }`.
- **Spec:** `tests/int/nightly/paid-body-select-leak.int.spec.ts` (108c64dd).
  It fails on TESTED_SHA and passes on the branch.
- **Fix status: fixed in aea5c099.**
  - Paid or free is decided from the stored document: `price` and `author` are
    read with `overrideAccess`, memoized per request in
    `req.context.paidBodyInfo`.
  - If that read fails, the content counts as paid.
  - A full doc that already has `price` and `author` skips the read.
  - The free-content, content-audio, expansion and visibility specs pass.
- **What to check:**
  - The extra `findByID` per partial read, for example on lists that select
    the body.
  - The per-request cache. A read, then a price change, then another read in
    the same request would see the old price. No such path exists today.

### N7 — The locked body works as a boolean oracle

- **Severity: Medium.** Confidence: confirmed.
- **Steps:** as anonymous, send
  `GET /api/contents?where[id][equals]=<paid>&where[body.root.children.children.text][like]=<word>&select=title`.
- **Expected:** the same answer whether the word is in the body or not.
- **Actual:** `totalDocs: 1` when the body contains the word and 0 when it does
  not. The text can be recovered word by word.
- **Cause:** the same one. Payload calls field access without a doc for a
  `where`, and `!doc?.price` then returned true.
- **Spec:** `tests/int/nightly/paid-body-query-oracle.int.spec.ts` (b40ac1fb).
- **Fix status: fixed in aea5c099.** Without a doc, only a super admin may
  filter on `body`. No app code filters on `body`.
- **What to check:** staff (curators) can no longer filter on the body over
  REST. That is intended.

### N9 — An anonymous nested GraphQL query brings the server down

- **Severity: High** (DoS). Confidence: confirmed. The process died twice
  during exploration.
- **Steps:** as anonymous, send `POST /api/graphql` with
  `{Contents(limit:50){docs{author{authoredContents{docs{…}}}}}}`, repeating
  `author{authoredContents{docs{` N times.
- **Expected:** a quick rejection or a quick answer.
- **Actual:**
  - N=2 takes 1.8 s and N=3 takes 19.8 s.
  - N=4 never answers, and the Node process dies (ECONNREFUSED until restart).
  - The 2-level query repeated under 30 aliases took 9.4 s.
- **Cause:** Payload's GraphQL has no limit that weighs join fields. Nothing in
  `src/payload.config.ts` set one. REST already clamps `depth`.
- **Spec:** `tests/int/nightly/graphql-nested-join-dos.int.spec.ts` (72bb06b8).
  It stops at 3 levels with an 8 s timeout so it never kills the server under
  test.
- **Fix status: fixed in bea6803b + 086fc313 + 63cab77e.** One graphql-js
  validation rule in `src/payload.config.ts`:
  - depth of at most 8 field levels;
  - at most 50 fields per operation, aliases and fragments included;
  - literal `limit` arguments of at most 100;
  - a budget on fragment re-expansion.
  - GraphQL stays enabled. A shallow query still answers 200.
- **What to check:**
  - 50 fields is tight for a large GraphQL client. Today neither the app nor
    the tests use GraphQL, and the admin panel uses REST.
  - A `limit` passed through a GraphQL variable is not visible during
    validation. Payload's `maxLimit` still applies to it, so consider setting
    one.
  - Alternative: disable GraphQL if it is not part of the product.

### N10 — The AI routes' rate limit is bypassed with `X-Forwarded-For`

- **Severity: Medium.** Confidence: confirmed locally. This is the hypothesis
  from 2026-11-14 and 2026-11-18, now with a spec.
- **Steps:** send `POST /api/speech` 45 times. From one client, requests 37–45
  get 429. With a different `x-forwarded-for` on each request, all 45 get 200.
- **Actual:** unlimited anonymous calls to the paid Groq and Fish routes
  (assistant, expand, plan-tour, speech, transcribe).
- **Cause:** `src/lib/rate-limit.ts:17` uses the first entry of
  `x-forwarded-for`, which the client writes itself.
- **Spec:** `tests/int/nightly/rate-limit-forwarded-for-bypass.int.spec.ts`
  (9560e00e).
- **Fix status: needs maintainer.** The right client IP depends on the
  production proxy, which is deployment config. Suggested patch: use the last
  entry appended by the trusted proxy, or a header only the proxy sets (e.g.
  `x-real-ip`), in `clientIp()` of `src/lib/rate-limit.ts`. Then adjust the
  nightly spec's expectation to that header.

### N12 — Image uploads have no size limit

- **Severity: Medium** (disk quota). Confidence: confirmed.
- **Steps:** a signed-in user sends a multipart `POST /api/contentImages` (or
  `usersPropics`) with a valid PNG plus 150 MB of padding.
- **Expected:** 413 or 400.
- **Actual:** 201. The uploader cannot delete the file afterwards
  (`contentImages` delete is super-admin only). The production deploy folder
  has a small quota (AGENTS.md).
- **Cause:** there is no `upload.limits.fileSize` in `src/payload.config.ts`,
  and no limit on either collection.
- **Spec:** `tests/int/nightly/upload-size-unlimited.int.spec.ts` (3c9473d6).
- **Fix status: needs maintainer.** The cap is a product decision.
  - Suggested patch: `upload: { limits: { fileSize: 10_000_000 } }` in
    `buildConfig`.
  - Check that it does not limit Mint model uploads or `contentAudio`
    (generated MP3 files).

### N14 — `createdBy` can be written by the client on contents

- **Severity: Low.** Confidence: confirmed on contents.
- **Steps:** as A, send `POST /api/contents` with `createdBy: <B>`. It answers
  201 and stores B. A `PATCH` of `createdBy` on A's own content works too.
- **Expected:** the server stamps the caller.
- **Impact:** false attribution. The same field decides ownership in
  `Objects.ts:46` and `QuizQuestions.ts:32`. There, a user can only give a
  document away; nobody can take one.
- **Cause:** the RBAC plugin adds `createdBy` (`src/payload.config.ts` ~232)
  without field access. This was already noted on 2026-11-14 and is now
  covered by a spec.
- **Spec:** `tests/int/nightly/content-createdby-spoof.int.spec.ts` (a7d0d97a).
- **Fix status: needs maintainer.** The fix touches the plugin's field across
  five collections. Suggested patch: a `beforeChange` hook shared by those
  collections that sets `createdBy = req.user.id` on create and keeps
  `originalDoc.createdBy` on update for anyone but a super admin.
